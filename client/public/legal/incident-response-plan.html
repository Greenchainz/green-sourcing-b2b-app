Security Incident Response Plan

Version 1.0  ·  Effective: April 19, 2026  ·  Review cycle: Annual  ·  Owner: CEO / founder@greenchainz.com

1. Purpose and Scope

This Incident Response Plan (IRP) defines how GreenChainz Inc. detects, contains, investigates, and recovers from security incidents affecting the GreenChainz platform and the data of its users. It applies to all system components: the production application hosted on Microsoft Azure Container Apps, the PostgreSQL database, all third-party integrations, and any personal data processed by GreenChainz.

3. Detection Sources

  • Sentry — Real-time application error monitoring and anomaly alerting
  • Azure Monitor / Application Insights — Infrastructure metrics, failed auth events, and anomalous traffic patterns
  • GitHub Advanced Security — Dependency vulnerability alerts (Dependabot) and code scanning (CodeQL)
  • Automated vulnerability scans — Scheduled quarterly scans via GitHub Actions (Snyk + Trivy)
  • External reports — Security researchers via security@greenchainz.com
  • User reports — Suspicious activity reported through the platform or support email

4. Response Procedures

Phase 1 — Identification (0–1 hour for Critical/High)

  1. Receive alert from detection source or external report
  2. Triage: confirm whether the event is a genuine incident or false positive
  3. Assign severity classification using Section 2 criteria
  4. Log the incident: date/time of detection, detection source, initial assessment, severity
  5. Notify CEO (Jerit Norville) immediately for Critical and High severity

Phase 2 — Containment

  1. Isolate affected components — Disable compromised accounts, revoke exposed API keys/secrets via Azure Key Vault, scale down or redeploy affected Container Apps
  2. Preserve evidence — Export Azure Monitor logs, Sentry event data, and database query logs before making changes
  3. Implement short-term fix — Block malicious IPs at Azure network level, rotate secrets, disable affected features if necessary
  4. Assess blast radius — Determine which users and data may have been affected

Phase 3 — Investigation

  1. Review application logs, auth logs, and database access logs for the incident window
  2. Identify the root cause (vulnerability, misconfiguration, credential compromise, etc.)
  3. Document the full timeline of the incident
  4. Determine exact scope of data potentially accessed or exfiltrated

Phase 4 — Notification

Regulatory notification (GDPR / breach reporting): If the incident involves personal data of EU/UK residents and poses a risk to individuals, GreenChainz will notify the relevant supervisory authority within 72 hours of becoming aware of the breach. If notification within 72 hours is not possible, the notification will include the reasons for the delay.

Affected user notification: Users whose personal data was likely compromised will be notified without undue delay, in plain language, describing what happened, what data was affected, and what steps they should take.

Microsoft notification: If the incident involves Microsoft customer data processed through the Microsoft commercial marketplace, Microsoft will be notified per the Microsoft Publisher Agreement obligations.

Phase 5 — Recovery

  1. Deploy permanent fix to production via standard GitHub Actions CI/CD pipeline
  2. Restore services from Azure-managed backups if data integrity was compromised
  3. Verify fix effectiveness with targeted testing
  4. Monitor for recurrence for 14 days post-incident
  5. Remove temporary containment measures once permanent fix is confirmed

Phase 6 — Post-Incident Review

  1. Conduct post-mortem within 7 days of resolution
  2. Document: what happened, what worked, what failed, root cause, corrective actions
  3. Update this IRP if gaps were identified
  4. Implement long-term controls to prevent recurrence
