# GreenChainz Multi-Agent Coding Workflow

This document outlines the architecture and execution flow for the GreenChainz multi-agent coding system, powered by Azure AI Foundry. It leverages the 17 specialized agents already deployed in the `greenchainz-resource` Foundry project.

## 1. System Architecture

The workflow follows a hierarchical routing and handoff pattern. The **workflow-agent** acts as the orchestrator, receiving the initial user prompt and breaking it down into specific tasks. These tasks are then routed to the specialized domain agents.

### The Agent Roster

Based on the deployed agents, the coding team consists of:

*   **Orchestrator:** `workflow-agent`
*   **Domain Specialists:**
    *   `frontend` (UI/UX, React, Tailwind)
    *   `db-agent` (Drizzle ORM, PostgreSQL schema, migrations)
    *   `auth` (better-auth, Microsoft/Google/LinkedIn providers)
    *   `mobile` (Expo, React Native)
    *   `Scraper` (Data ingestion, parsing)
    *   `coder` / `coder2` (General backend logic, API routes)
*   **Quality Assurance & Deployment:**
    *   `qa-orchestrator-agent` (Code review, security checks, testing)
    *   `docker-agent` (Containerization, Azure Container Apps config)

### Data & Context

All agents will be augmented with an Azure AI Search integration (`greenchainz-search`), indexing the live `greenchainz-db-prod` PostgreSQL database. This provides the "GreenChainz brains," allowing agents to query the current schema, existing materials, and business logic when generating code.

## 2. Execution Flow

The workflow operates in four distinct phases:

### Phase 1: Ingestion & Planning (The Orchestrator)

1.  **User Prompt:** The user submits a high-level request (e.g., "Build a new supplier dashboard for tracking RFQs").
2.  **Analysis:** The `workflow-agent` receives the prompt, analyzes the requirements, and queries the AI Search index to understand the existing context (e.g., "What does the `rfqs` table look like?").
3.  **Task Decomposition:** The orchestrator breaks the request into sub-tasks (e.g., 1. Update DB schema, 2. Build API route, 3. Build React component).

### Phase 2: Execution (The Specialists)

The orchestrator routes the sub-tasks to the relevant specialists sequentially or in parallel, depending on dependencies:

1.  **Database:** `db-agent` writes the Drizzle schema updates and migration scripts.
2.  **Backend:** `coder2` writes the tRPC router procedures, utilizing the new schema.
3.  **Frontend:** `frontend` builds the React components, wiring them to the tRPC endpoints.

*Handoff Logic:* The orchestrator passes the output of one agent as context to the next. For example, the `frontend` agent receives the API contract generated by `coder2`.

### Phase 3: Review & Validation (QA)

1.  **Code Review:** The `qa-orchestrator-agent` reviews the combined output from all specialists.
2.  **Validation:** It checks against the GreenChainz architectural standards (e.g., enforcing `better-auth`, checking for hardcoded secrets, ensuring Drizzle is used).
3.  **Feedback Loop:** If issues are found, the QA agent sends the code back to the specific specialist with correction instructions.

### Phase 4: Deployment Prep (Docker)

1.  **Containerization:** Once QA approves, the `docker-agent` updates any necessary `Dockerfile` or Azure Container Apps configuration (`containerapp.yaml`).
2.  **Final Output:** The orchestrator compiles the final, validated code and deployment instructions, presenting them to the user.

## 3. Implementation Details

The system will be built using Python and the `azure-ai-projects` SDK. It will use the `ResponseStreamEventType.RESPONSE_OUTPUT_ITEM_ADDED` and `workflow_action` events to track the handoff between agents, as demonstrated in the Azure AI Foundry sample code.

The Python script will initialize the `AIProjectClient`, define the workflow routing logic, and stream the multi-agent conversation back to the console.
