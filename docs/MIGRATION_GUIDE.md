# GreenChainz — Database Migration Safety Guide

> **Read this before running any Drizzle migration in a production environment.**

This guide covers safe migration patterns for a live B2B platform. Violations of these rules have caused production outages and data loss at real companies. Follow them exactly.

---

## Core Rules (Non-Negotiable)

### 1. Never use `drizzle-kit push` in production

`drizzle-kit push` applies DDL changes directly to the database without generating migration files. This means:
- No audit trail — impossible to tell what changed
- No rollback path — you can't undo it with a migration
- Non-deterministic across environments — staging and production diverge silently

**Use `drizzle-kit generate` + `drizzle-kit migrate` exclusively.**

```bash
# ✅ Safe — creates a versioned SQL file and applies it
pnpm run db:generate
pnpm run db:migrate

# ❌ Never — destroys audit trail, breaks rollbacks
pnpm run db:push
```

### 2. Migrations run ONCE, in a dedicated job, BEFORE traffic shifts

Never run `drizzle-kit migrate` inside the application startup path (`server/_core/index.ts`). If you do:
- Multiple container replicas will race to apply the same migration
- One replica will win; others will fail mid-request with lock errors
- Drizzle's `__drizzle_migrations` table does NOT lock for distributed concurrency

The `deploy-azure.yml` workflow already gates migrations behind the Production environment approval step and runs them in a dedicated `migrate` job before the `deploy` job starts. Keep it that way.

### 3. Commit migration files

After `drizzle-kit generate`, **always commit all three**:
- `drizzle/XXXX_<description>.sql` — the generated SQL
- `drizzle/meta/XXXX_snapshot.json` — the schema snapshot Drizzle uses for drift detection
- `drizzle/meta/_journal.json` — the migration journal Drizzle reads to discover ordered migrations

These must be committed before the PR merges. They are part of your code history.

## Large-Table Index Safety

### Problem

Drizzle generates `CREATE INDEX IF NOT EXISTS ...` by default. On a table with millions of rows, this holds a lock that **blocks all writes** until the index is built. For the `rfqs`, `rfq_bids`, or `materials` tables, this could mean minutes of downtime.

### Solution: `CREATE INDEX CONCURRENTLY`

After running `drizzle-kit generate`, open the generated SQL file and manually edit any `CREATE INDEX` on a large table:

```sql
-- ❌ Generated by Drizzle — blocks writes for duration of index build
CREATE INDEX IF NOT EXISTS "rfq_bids_rfq_id_idx" ON "rfq_bids" ("rfq_id");

-- ✅ Manual edit — does NOT lock the table
CREATE INDEX CONCURRENTLY IF NOT EXISTS "rfq_bids_rfq_id_idx" ON "rfq_bids" ("rfq_id");
```

### Important constraint: CONCURRENTLY cannot run in Drizzle's migration transaction

Production runs `pnpm db:migrate`, and Drizzle's PostgreSQL migrator executes pending migrations inside a transaction. `CREATE INDEX CONCURRENTLY` **cannot run inside that transaction**.

Because the transaction is opened by the migrator, deleting `BEGIN`/`COMMIT` text from generated SQL files (or splitting files) does not make `CONCURRENTLY` valid in `pnpm db:migrate`.

Use a dedicated autocommit `psql` or script step for `CREATE INDEX CONCURRENTLY`, and record successful execution in the deployment runbook before shifting traffic.

### Which tables require CONCURRENTLY?

Apply this rule: if the table has > 100,000 rows in production **or** will grow beyond that, use CONCURRENTLY.

Current candidates (check row counts before deciding):
- `rfqs`
- `rfq_bids`
- `materials`
- `supplier_profiles`
- `audit_logs`
- `notifications`

## The Expand-and-Contract Pattern for Destructive Changes

Destructive changes include:
- Renaming a column
- Dropping a column
- Changing a column's type
- Moving data between tables

You **cannot** do these in a single deployment. The application and database must always be compatible during the transition.

### Phase 1: Expand (add the new structure, keep the old)

```sql
-- Add the new nullable column; backfill it in a later step
ALTER TABLE "rfqs" ADD COLUMN "buyer_user_id" integer;
```

Deploy application code that **writes to both** `architect_id` (old) **and** `buyer_user_id` (new), reads from `architect_id`.

### Phase 2: Backfill (populate the new column)

Run in bounded batches to avoid row-locking the table:

```sql
-- Safe batched backfill — process 1000 rows at a time, skip locked rows
WITH batch AS (
  SELECT id FROM rfqs
  WHERE buyer_user_id IS NULL
  LIMIT 1000
  FOR UPDATE SKIP LOCKED
)
UPDATE rfqs
SET buyer_user_id = architect_id
WHERE id IN (SELECT id FROM batch);
```

Run this SQL repeatedly (cron job or manual script) until all rows are backfilled. Verify completion:

```sql
SELECT COUNT(*) FROM rfqs WHERE buyer_user_id IS NULL;
-- Should return 0 before proceeding
```

### Phase 3: Switch reads (application reads new column)

Deploy application code that reads from `buyer_user_id`, continues writing to both.

### Phase 4: Remove old writes

Deploy application code that writes only to `buyer_user_id`.

### Phase 5: Contract (drop the old column)

Wait at least 1 full deployment cycle (ideally several days) to confirm no rollback is needed, then:

```sql
-- Safe to drop now — no code reads or writes this column
ALTER TABLE "rfqs" DROP COLUMN "architect_id";
```

## Financial Data: Store as Integer Cents

**This is a known risk in the current schema.** Several columns use `decimal(10,2)` or `real` for monetary values. These must be migrated to integer cents.

### Why this matters

- `real` is a 32-bit IEEE 754 float. `0.1 + 0.2 != 0.3` in floating point. Never store money as float.
- `decimal(10,2)` is safer but still requires careful handling. For procurement software where values are displayed, computed, and compared, integers are the industry standard.

### Correct pattern

```typescript
// ❌ Schema as it exists today
pricePerUnit: decimal("price_per_unit", { precision: 10, scale: 2 }),

// ✅ Target pattern
pricePerUnitCents: bigint("price_per_unit_cents", { mode: "number" }),  // $10.50 → 1050
```

### Migration approach

Use expand-and-contract (see above). The backfill SQL:

```sql
UPDATE catalog_items
SET price_per_unit_cents = ROUND(price_per_unit::numeric * 100)::bigint
WHERE price_per_unit_cents IS NULL;
```

## Missing Foreign Key Indexes

Drizzle does **not** automatically create indexes for foreign key columns. A JOIN on an unindexed FK column causes a full table scan — catastrophic at scale.

### Current schema gaps to fix

After each schema change, verify that every FK column has a corresponding index. Drizzle schema syntax:

```typescript
// ❌ FK without index — full table scan on JOIN
export const rfqBids = pgTable("rfq_bids", {
  rfqId: integer("rfq_id").references(() => rfqs.id),
});

// ✅ FK with explicit index
export const rfqBids = pgTable(
  "rfq_bids",
  {
    rfqId: integer("rfq_id").references(() => rfqs.id, { onDelete: "cascade" }),
  },
  (table) => ({
    rfqIdIdx: index("rfq_bids_rfq_id_idx").on(table.rfqId),
  }),
);
```

### Referential integrity: always declare `onDelete`

Never omit the `onDelete` behavior. Omitting it defaults to the PostgreSQL database engine default (usually `NO ACTION`), which causes `ForeignKeyViolation` errors when deleting parent records.

| Relationship | Recommended `onDelete` |
|-------------|----------------------|
| Bid belongs to RFQ | `cascade` (delete bids when RFQ is deleted) |
| RFQ belongs to User | `restrict` (cannot delete a user with open RFQs) |
| Notification belongs to User | `cascade` (delete notifications with user) |
| Audit log belongs to User | `set null` (preserve audit log, nullify user reference) |

## Pre-Migration Checklist

Before applying any migration to production:

- [ ] Migration file committed to git
- [ ] Migration file reviewed for destructive operations (DROP, RENAME, ALTER TYPE)
- [ ] Large-table indexes modified to use `CONCURRENTLY`
- [ ] `CONCURRENTLY` indexes removed from transaction blocks
- [ ] Destructive changes use expand-and-contract (not a single-step DROP)
- [ ] Backfill for new columns ran and completed (0 NULL rows verified)
- [ ] Migration tested against staging with real schema size
- [ ] Rollback SQL prepared and tested
- [ ] Application code deployed to staging compatible with both old and new schema

## Rollback SQL Templates

### Drop an index if a migration goes wrong

```sql
-- DROP INDEX CONCURRENTLY cannot run inside a transaction block.
-- Run this outside a transaction (remove BEGIN/COMMIT if present in the migration file).
DROP INDEX CONCURRENTLY IF EXISTS "rfq_bids_rfq_id_idx";
```

### Restore a dropped column (if within the same transaction)

```sql
-- Only works if migration was in a transaction that hasn't committed
ROLLBACK;
```

### Manually recover from a failed migration (emergency)

Deleting the migration journal row is **not** a safe default recovery procedure. If
the migration was partially applied, re-running it can cause data corruption or
duplicate operations.

**Preferred: forward repair migration**

Create a new migration file that corrects the schema to the desired state and
add it via the normal `pnpm run db:generate` + `pnpm run db:migrate` flow.
This preserves the audit trail and is safe for destructive or non-transactional
migrations.

**Last resort: manual journal manipulation** (only if the migration was completely
rolled back and the schema is verified to be in the pre-migration state)

```sql
-- Check current migration state
SELECT * FROM __drizzle_migrations ORDER BY created_at DESC LIMIT 10;

-- ⚠️ DANGER: Only remove the entry if you have manually verified:
--   1. The schema matches the state BEFORE this migration ran
--   2. The migration is safe to re-run from scratch
--   3. No other migrations depend on this one's outcome
DELETE FROM __drizzle_migrations 
WHERE hash = '<migration-hash>';
```

> ⚠️ If you delete the journal entry and the schema is not fully reverted, the
> next `pnpm run db:migrate` will re-apply the migration against a partially
> changed schema and may corrupt data.
